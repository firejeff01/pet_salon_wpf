# 需求變更 Spec：客戶回饋第二輪（自填資料、刪除與店家簽名）

產出日期：2026-08-18  
決策確認日期：2026-08-18  
適用範圍：WPF 桌面系統 `pet_salon_wpf`  
前置規格：`pm/spec_contract_pdf_customer_feedback_changes.md`

## 1. 背景

客戶回報顧客自填頁的備註無法正確保存、誤存的顧客資料無法刪除、自填頁缺少病史與晶片狀態，並希望店家手寫簽名可保存後重複套用到契約 PDF。

本輪需求延續前一輪「飼主不需要在系統內簽名」的決策，但新增店家端的預存簽名能力。飼主簽名與甲方簽章仍保留空白，店家簽名只套入美容人員簽名與乙方簽章。

## 2. 使用者角色

- 顧客／飼主：在「客戶填寫」頁輸入本人與毛孩資料。
- 店家人員：協助確認重複資料、管理飼主資料、管理店家簽名及產生契約 PDF。
- 系統：執行資料驗證、交易式儲存、刪除保護、簽名套用與備份還原。

## 3. 需求目標

1. 顧客填寫的飼主與寵物備註可以保存並於後台重新讀取。
2. 顧客自填送出採整批成功或整批失敗，避免留下半套或重複 Owner。
3. 店家可以安全刪除沒有歷史紀錄的誤建顧客資料。
4. 自填頁可表達病史及晶片狀態，且不自行推論未填內容。
5. 店家可保存多組手寫簽名或匯入簽名圖片，設定預設簽名並套用到 PDF 店家簽名位置。

## 4. 功能需求

### R1. 顧客自填備註

- 顧客資料區新增「飼主備註」，儲存至 `Owner.Note`。
- 每一個毛孩資料區新增「寵物備註」，儲存至該筆 `Pet.Note`。
- 兩種備註皆為選填，最多 1000 字。
- 顧客送出成功後，店家於飼主管理及寵物編輯頁重新開啟資料時，內容需與送出值一致。
- 備註不新增至契約 PDF；本輪只要求保存與後台維護。

### R2. 自填資料交易與重複警告

- 顧客送出時，系統先驗證 Owner 與所有有填寵物名稱的 Pet。
- 全部驗證通過後，Owner 與 Pets 必須在同一資料庫交易中建立。
- 任一 Owner 或 Pet 驗證失敗時，整批不得新增任何資料。
- 送出處理中不可再次送出，以避免連點建立重複資料。
- 若身分證字號或電話與既有 Owner 完全相同，系統顯示「可能重複」警告。
- 由店家決定：
  - 選擇取消：不新增任何資料，保留畫面輸入供修改。
  - 選擇仍要建立：繼續交易式建立，不以重複檢查直接禁止。
- 不新增身分證字號或電話的資料庫唯一索引。

### R3. 飼主資料刪除

- 飼主管理頁提供「刪除飼主」操作。
- 刪除前顯示飼主姓名、寵物數量及「此動作無法復原」。
- 使用者取消確認時不得刪除任何資料。
- Owner 與其所有 Pets 都沒有任何 Appointment / GroomingRecord 時，可在單一交易中先刪除 Pets，再刪除 Owner。
- Owner 或任一 Pet 已有 Appointment 或 GroomingRecord 時，禁止永久刪除，並顯示需保留歷史紀錄的原因。
- 不將既有 EF 關聯全面改為 Cascade Delete。
- 封存／停用不在本輪範圍。

### R4. 自填頁病史

- 每隻毛孩顯示 `MedicalHistoryOptions.All` 的完整病史選項。
- 「以上皆無」與其他病史互斥：
  - 勾選「以上皆無」時取消所有其他病史。
  - 勾選任一其他病史時取消「以上皆無」。
- 勾選「其它」時顯示自由文字欄位，儲存至 `Pet.MedicalHistoryOther`。
- 最終選項儲存至 `Pet.MedicalHistory`。
- 既有 `PetEditViewModel` 與 `GroomingPageViewModel` 的病史語意及 PDF 規則維持不變。

### R5. 自填頁晶片狀態

- 每隻毛孩提供三態晶片狀態：「未填」、「有」、「無」。
- 初始值為「未填」，不得因晶片號碼空白自行推論為「無」。
- 選擇「未填」：`ChipNumber = null` 且 `UnregisteredIdMethod = null`。
- 選擇「有」：顯示晶片號碼欄位且為必填；未填不得送出。儲存後 `ChipNumber` 為輸入值，`UnregisteredIdMethod = null`。
- 選擇「無」：可填替代識別方式；若留空則儲存 `UnregisteredIdMethod = "無"`，並令 `ChipNumber = null`。
- 此映射需符合既有 R3 PDF 規則：只有 `UnregisteredIdMethod` 有值時才勾選「無／未登記」。

### R6. 多組店家簽名管理

- 店家人員可建立多組店家簽名 profile。
- 每個 profile 具有唯一識別碼、顯示名稱、PNG 簽名圖、建立／更新時間及是否為預設。
- 簽名來源支援：
  - 在系統 `SignaturePad` 內手寫後保存。
  - 匯入 PNG 或 JPEG 圖片。
- 系統將輸入正規化為裁切過、透明背景且大小受限制的 PNG。
- 可預覽、重新命名、設為預設及刪除 profile。
- 同一時間最多一組預設簽名；設定新預設時取消舊預設。
- 刪除 profile 前需確認；刪除預設 profile 後可處於沒有預設簽名的狀態，不自動猜選其他 profile。
- 簽名資料儲存在應用程式資料目錄的 `signatures/`，不新增 SQLite schema。
- 應用程式備份與還原需包含簽名 metadata 與 PNG。

### R7. PDF 套用店家簽名

- 開啟契約預覽時自動選取預設店家簽名；若無預設，維持未選取。
- 店家可在契約預覽對話框切換簽名 profile。
- 切換後需更新預覽；正式 PDF 必須使用與最後預覽相同的簽名快照。
- 選定簽名同時套入：
  - page 1「美容人員簽名」
  - page 4「乙方簽章」
- 以下位置永遠保持空白，不套入店家簽名：
  - page 1「飼主簽名」
  - page 4「甲方簽章」
- 沒有選定簽名時仍可產生 PDF，所有簽名欄維持空白。
- 選定簽名檔遺失、損毀或無法讀取時：顯示警告、店家簽名欄保持空白，但仍允許產生 PDF。
- 已產生的舊 PDF 不回溯修改；契約版本及檔名規則維持不變。

## 5. 資料與儲存決議

### 5.1 SQLite

- 不新增資料表或欄位。
- 沿用 `Owner.Note`、`Pet.Note`、`Pet.ChipNumber`、`Pet.UnregisteredIdMethod`、`Pet.MedicalHistory`、`Pet.MedicalHistoryOther`。

### 5.2 店家簽名檔案

```text
{app-data}/
  signatures/
    profiles.json
    {signature-id}.png
```

- metadata 中只保存相對路徑，不接受根目錄外路徑。
- JSON 與 PNG 儲存需避免只完成其中一半。
- 備份還原時需防止路徑穿越，且只能還原至 `signatures/`。

## 6. 安全與隱私

- 手寫簽名視為敏感個資，錯誤訊息與日誌不得輸出簽名 Base64。
- 匯入檔案需實際解碼驗證，不可只信任副檔名。
- 拒絕 SVG、HTML、外部 URL、毀損圖片及超出系統限制的圖片。
- PDF 只嵌入系統重新編碼的 PNG data URI。
- Owner 刪除必須經確認且受歷史資料政策保護。
- 所有多實體新增／刪除操作必須具備交易一致性。

## 7. 不在本輪範圍

- 飼主電子簽章、身分驗證、憑證式數位簽章或法律驗章。
- 對既有 PDF 回填新簽名。
- Owner 封存／停用。
- 自動合併重複 Owner。
- 對身分證字號或電話建立 unique index。
- 將 Owner.Note 或 Pet.Note 顯示於契約 PDF。

## 8. 驗收摘要

- 顧客可保存飼主及每隻寵物備註。
- 自填資料不會因後段驗證失敗留下 Owner。
- 重複資料只警告，不直接禁止。
- 無歷史的誤建 Owner 可連同 Pets 刪除；有歷史則阻擋。
- 病史與晶片三態正確保存並符合既有 PDF 語意。
- 可保存多組簽名、設定預設、於預覽選擇並套入兩個店家簽名位置。
- 飼主／甲方簽名保持空白。
- 簽名異常不阻擋 PDF，但必須警告。
- 備份與還原包含簽名資料。
