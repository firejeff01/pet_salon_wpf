# 需求變更 Spec：客戶反饋之契約 PDF 與資料表調整

產出日期：2026-05-16
最後更新：2026-05-16（PM Review 補強版）
來源文件：`pm/客戶反饋.docx`（已抽純文字至 `pm/_feedback_extracted.txt`、圖片描述見本文附錄 A）
適用範圍：WPF 桌面系統（pet_salon_wpf）— 飼主／寵物資料維護、服務紀錄填寫、契約 PDF 產生流程與契約 PDF 版面
本 Spec 不涵蓋：`pm/spec_pet_salon.md` 原始規格（該為初版），本次僅針對客戶反饋帶來的 R1–R8 變更需求。

## 1. 背景

客戶於試用後回饋目前契約 PDF 與資料表輸出有多處不符合現場使用方式，主要問題包含：

- 部分欄位被系統強制必填或自動帶值，但現場希望保留空白。
- PDF 最後一頁服務資料表（page 4）每次服務內容會變動，應優先放在 PDF 第一頁。
- PDF 資料表部分選項未完整呈現，例如「異常」狀態與「以上皆無」病史。
- 契約條款下方的短版文字（page 4 末尾的 8 點條款）目前有錯字／文意斷裂，客戶已提供應替換的原始文字。
- 甲方簽章／飼主簽名線會自動印出飼主姓名，現場希望由飼主紙本親簽。

涉及之既有領域元件（用語對齊 `src/PetSalon.Core/Entities/`、`src/PetSalon.Core/Constants/`）：

- `Owner`（飼主，含 `EmergencyContactName / EmergencyContactPhone / EmergencyContactRelationship` 三欄）
- `Pet`（寵物，含 `ChipNumber : string?`、`UnregisteredIdMethod : string?`、`MedicalHistory : List<string>`、`PhysicalExamination` 子物件）
- `PhysicalExamination`（眼睛／耳朵／牙齒／四肢／皮膚／皮毛，皆為 `string`，預設 "正常"；對應 `BodyConditionOptions.Standard = { "正常", "異常" }`、皮毛另支援「打結」、「跳蚤壁蝨」）
- `MedicalHistoryOptions.All`（18 項，目前無「以上皆無」）
- `GroomingRecord` 與其關聯之 `ContractVersion`
- 契約 PDF 模板：`src/PetSalon.Infrastructure/Pdf/Templates/contract.hbs`（4 個 `<section class="page">` 區塊）

## 2. 變更目標

1. 降低現場建檔阻礙：緊急聯絡人三欄改為選填。
2. 契約 PDF 簽署方式定調為「紙本親簽」：不要求系統內手寫簽名圖，且 PDF 簽名線一律保持空白、不自動帶名字。
3. 修正 PDF 服務資料表輸出邏輯：晶片狀態不再以空白自動推論、異常身體狀態如實呈現、寵物病史新增「以上皆無」。
4. 調整 PDF 頁面順序：服務資料表（目前 page 4）移為 PDF 第一頁。
5. 替換 PDF 服務資料表頁下方的短版同意文字與 1~8 點條款為客戶提供之原始文字。

## 3. 使用者角色

- 櫃台／美容人員：建立 Owner、Pet 與 GroomingRecord，產生契約 PDF。
- 飼主：於 PDF 列印後在紙本簽名欄親自簽署。

## 4. 需求項目

### R1. 緊急聯絡人欄位取消必填

作為櫃台／美容人員，當我建立或編輯 Owner 資料時，我可以不填緊急聯絡人、與飼主關係、緊急聯絡電話，仍可儲存並產生契約 PDF。

對應欄位：`Owner.EmergencyContactName`、`Owner.EmergencyContactRelationship`、`Owner.EmergencyContactPhone`。

驗收準則：

- Owner 表單／客戶資料頁中，上述三欄不得標示為必填（不顯示紅星或必填提示）。
- 三欄未填寫時，儲存／編輯不得出現必填驗證錯誤訊息，亦不得阻擋送出。
- 三欄未填寫時，契約 PDF 對應儲存格（page 1「(二) 消費者/飼主」表的「緊急聯絡人」、「緊急聯絡人電話」，以及 page 4 服務資料表中「緊急聯絡人 / 與飼主關係 / 緊急聯絡電話」三列）顯示為空白，**不得**顯示 `null`、`未填寫`、`-`、預設文字或樣板殘留字串。
- 若 `EmergencyContactRelationship` 為空但 `EmergencyContactName` 有值，page 1 表格中括號部分不得輸出空括號 `()`（目前 hbs 第 123 行已用 `{{#if owner.emergencyContactRelationship}}` 包覆，需保留此行為）。
- 既有已填寫之緊急聯絡人資料不得因此次變更被清空或遺失。

### R2. 移除「系統內手簽」之要求

作為櫃台／美容人員，當我產生契約 PDF 時，不需要先在系統內要求飼主於畫布上手寫簽名。

說明：經 PM 確認，wpf 版本目前模板（`contract.hbs`）的簽章欄即為紙本簽名線設計（page 3「甲方簽章 / 乙方簽章」、page 4「飼主簽名 / 美容人員簽名」），並未嵌入手寫簽名圖。客戶所稱「系統上手簽的地方可以刪除」指的是若 UI 有任何要求飼主於螢幕簽名的步驟，需移除。

驗收準則：

- 產生契約 PDF 流程不得因「缺少系統內飼主簽名 / 店家簽名」而阻擋。
- 若 UI（如服務紀錄頁 / 契約產生對話框）目前有「簽署契約」彈窗、簽名畫布、簽名清除鈕、確認簽名鈕等控制項，需從產 PDF 主流程移除（或隱藏）。
- PDF 模板保留紙本可簽署之空白簽名線。
- 不再將任何「飼主簽名圖」、「店家簽名圖」嵌入 PDF；模板現有的 `<span class="blank wide">` 簽名線維持空白線條樣式。
- 移除手簽流程後，相關設定檔／JSON Schema 若曾保存簽名 Base64 欄位，需確認不再寫入新值（既有資料不主動清理）。

### R3. 晶片號碼空白時不得自動勾選「未登記 / 無」

作為櫃台／美容人員，當寵物未填晶片號碼時，PDF 不應自動將「未登記 / 無」勾選格塗黑。

對應欄位：`Pet.ChipNumber : string?`、`Pet.UnregisteredIdMethod : string?`。
對應模板位置：
- `contract.hbs` 第 100 行（page 1）：`<span class="cb {{#unless pet.chipNumber}}on{{/unless}}"></span>若未登記，身份識別方式：{{pet.unregisteredIdMethod}}`
- `contract.hbs` 第 307 行（page 4）：`<span class="cb {{#unless pet.chipNumber}}on{{/unless}}"></span>無`

驗收準則：

- `Pet.ChipNumber` 為空白／`null` 時，PDF 之「晶片號碼」儲存格顯示空白。
- `Pet.ChipNumber` 為空白／`null` 時，page 1 之「若未登記」與 page 4 之「無」勾選格**預設不勾選**（拆除原本 `{{#unless pet.chipNumber}}` 自動判斷）。
- 改以 `Pet.UnregisteredIdMethod` 是否有值決定 page 1 之「若未登記」勾選狀態：當 `UnregisteredIdMethod` 不為空時才勾選，並於該行顯示其身份識別方式內容。
- page 4 之「無」勾選格之判定條件變更為：當使用者明確於 Pet 編輯介面標示「無晶片」時才勾選。具體做法見「資料模型決議」段落，採用「以 `UnregisteredIdMethod` 是否有值」作為共用判定（不新增專用布林欄位，理由：避免兩個來源真實值不同步；同時對齊 page 1 既有設計）。
- Pet 編輯 UI 需提示使用者：若無晶片號碼，請在「身份識別方式」欄位填寫替代識別方式（如「無晶片，以項圈牌號 A12 識別」或單純填「無」）；填寫後 PDF 才會勾選未登記／無。
- 既有資料：若 `ChipNumber` 與 `UnregisteredIdMethod` 都為空之 Pet，PDF 兩處勾選格皆不勾選、兩處文字儲存格皆空白（為符合「不自行推論」原則）。

### R4. 契約 PDF 頁面順序調整：服務資料表移至第一頁

作為櫃台／美容人員，我希望每次服務會變動的「寵物美容契約書／服務資料表」（目前 `contract.hbs` 之 page 4）出現在契約 PDF 第一頁，方便快速核對與列印當次資料。

驗收準則：

- 調整後 PDF 頁序為：
  1. 新 page 1：服務資料表（原 page 4 內容，含 owner 基本資料表、服務項目、寵物個性、儲值金額、獸醫院、寵物身體狀態檢視、寵物病史、狀況良好條文、＊段同意文字、1~8 點條款、簽名日期區）
  2. 新 page 2：原 page 1 內容（簽約注意事項、一、基本資料、二、美容服務預約、三、犬/貓健康狀況前段）
  3. 新 page 3：原 page 2 內容（三、健康狀況風險告知後段、四、乙方責任、五、甲方義務及責任前段）
  4. 新 page 4：原 page 3 內容（六、契約解除及終止之退費方式、七、其他事項、簽署人聲明、甲方／乙方簽章、簽署日期）
- 頁面搬移後不得造成表格截斷、文字重疊、跨頁殘行或頁尾簽名欄跑版。
- 各頁 `<section class="page">` 之 CSS（`page-break-after`）需相應檢查，最後一頁仍維持 `:last-child` 不強制分頁。
- PDF 總頁數維持 4 頁。
- 任何頁碼／頁眉文字（目前無）若未來加上，需依新頁序對齊；本次不主動新增頁碼。

### R5. 簽名欄不得自動帶入甲方／飼主姓名；美容人員簽名亦保持空白

作為飼主，我希望 PDF 之簽名線保持空白，由我在紙本列印後親簽。

對應模板位置：
- `contract.hbs` 第 239 行：`<div>甲方簽章：<span class="blank wide">{{owner.name}}</span></div>` → 需移除 `{{owner.name}}`。
- `contract.hbs` 第 432 行：`<div style="margin-left:8mm;">飼主簽名：<span class="blank wide">{{owner.name}}</span></div>` → 需移除 `{{owner.name}}`。
- `contract.hbs` 第 433 行：`美容人員簽名：<span class="blank wide"></span>` → 本來即為空，維持空白即可（客戶圖 3 圈起此處的訴求為「確認後續不要回頭做自動帶入」）。

驗收準則：

- 新 page 4（原 page 3）之「甲方簽章」線不得帶入 `Owner.Name`，呈現可簽名之空白線。
- 新 page 1（原 page 4）之「飼主簽名」線不得帶入 `Owner.Name`，呈現可簽名之空白線。
- 新 page 1 之「美容人員簽名」線保持空白（不帶任何美容師／員工姓名，目前模板即為空白，僅需確保未來不誤加變數）。
- 「乙方簽章」目前模板硬編「貳寶寵物美容工坊」（hbs 第 240 行）→ **本次不變更**，列為待業主確認事項（見第 7 節 Q2）。
- 簽名線寬度保持目前 `.blank.wide`（`min-width: 50mm`）以利紙本書寫。
- 簽名日期 `中華民國 {{rocYear}} 年 {{rocMonth}} 月 {{rocDay}} 日` 是否一併保持空白由業主確認；本次預設行為**維持現狀**（系統帶入今日民國年月日），理由：客戶反饋未提及日期欄。

### R6. 身體狀態檢視之「異常」狀態必須寫入 PDF

作為美容人員，當我於系統中將寵物身體狀態填為「異常」時，PDF 需如實顯示該異常結果，而非只渲染「正常」勾選格。

對應資料模型：
- `PhysicalExamination.Eyes / Ears / Teeth / Limbs / Skin / Fur`：型別為 `string`，合法值來自 `BodyConditionOptions.For(part)`。
  - 眼睛／耳朵／牙齒／四肢／皮膚：`"正常"` 或 `"異常"`。
  - 皮毛：`"正常"`、`"打結"`、`"跳蚤壁蝨"`（皮毛已是多選——模板第 360–363 行確實已渲染 `furOptions` 中的「打結」、「跳蚤壁蝨」；但「異常」未含於此清單）。
- `Pet.PhysicalExamination` 與 `GroomingRecord.PhysicalExamination` 兩處皆有此物件，PDF 顯示需以 `GroomingRecord.PhysicalExamination` 為準（PDF 為當次服務文件）。

對應模板位置（皆於 page 4 / 變更後為 page 1）：第 334–363 行，6 個 `<td class="val">N.部位　<span class="cb {{#ifEq ... '正常'}}on{{/ifEq}}"></span>正常</td>`。

驗收準則：

- 1.眼睛、2.耳朵、3.牙齒、4.四肢、5.皮膚 5 個項目，PDF 需同時呈現「□正常」與「□異常」兩個勾選格，並依當次 `GroomingRecord.PhysicalExamination` 之值勾選對應格。
- 6.皮毛項目，PDF 需呈現「□正常」、「□異常」、「□打結」、「□跳蚤壁蝨」四個勾選格（其中「打結」、「跳蚤壁蝨」對應現有 `furOptions` 清單；「異常」對應 `PhysicalExamination.Fur == "異常"`）。
- 當部位為「正常」時，僅勾選「正常」；當為「異常」時，僅勾選「異常」；任一情況下兩格不可同時勾選。
- 若該部位欄位為空字串／`null`（理論上不應發生，預設 "正常"），PDF 兩格皆不勾選。
- 系統 UI（Pet 編輯頁與 GroomingRecord 填寫頁）需提供「正常／異常」單選控制項，且寫入 PDF 之值需與 UI 顯示一致。
- 本次不要求新增「異常補充說明文字」欄位（資料模型尚無此欄位），若業主後續希望支援「異常 + 文字描述」屬於延伸需求，列入待確認 Q5（見第 7 節）。

### R7. 寵物病史新增「以上皆無」選項

作為美容人員，當寵物沒有列出的病史時，我需要能勾選「以上皆無」，並讓 PDF 同步顯示。

對應資料：`MedicalHistoryOptions.All`（目前 18 項）、`Pet.MedicalHistory : List<string>`、`GroomingRecord.MedicalHistory : List<string>`。
對應模板位置：`contract.hbs` 第 377–406 行（page 4 寵物病史區塊）。

驗收準則：

- `MedicalHistoryOptions.All` 新增第 19 項常數 `"以上皆無"`，置於清單末尾（不破壞既有順序，使既有資料 index 不變）。
- Pet 編輯 UI、GroomingRecord 填寫 UI 之病史多選控制項均可選擇「以上皆無」。
- PDF 寵物病史區塊新增「□以上皆無」勾選格，建議置於第 3 列末尾（與「傳染性疾病」、「其它」同列）。
- 互斥規則：
  - 當使用者於 UI 勾選「以上皆無」時，其他病史選項自動取消；
  - 當使用者勾選任一具體病史時，「以上皆無」自動取消；
  - 「以上皆無」與「其它」亦互斥（其它代表有未列出之病史，與以上皆無語意衝突）。
- 互斥規則由 UI 端／ViewModel 端負責執行；後端不需要新增資料驗證（避免 Json schema 變更）。
- PDF 渲染時依 `MedicalHistory` 中是否包含字串 `"以上皆無"` 決定勾選。
- 既有 Pet 資料：`MedicalHistory` 為空陣列 `[]` 之 Pet，PDF 上「以上皆無」**不自動勾選**（依本變更需求 R3 同理「不自行推論」原則）；若業主希望「空陣列＝以上皆無」自動勾選屬於行為變更，列入待確認 Q6（見第 7 節）。

### R8. PDF 條款短版文字（page 4 末尾）改用客戶提供原文

作為業主，我希望服務資料表下方的同意文字與 1~8 點條款正確可讀，不要出現錯字或文意斷裂。

對應模板位置：`contract.hbs` 第 413–425 行（page 4 之 ＊段 + ol 1~7 點，目前實際只有 7 項且文字錯亂）。

驗收準則：

- 替換 `contract.hbs` 第 413–415 行之 `<p>` 同意文字為客戶提供之 ＊段原文（見下方原文）。
- 替換 `contract.hbs` 第 416–425 行之 `<ol>` 為客戶提供之 1~8 點條款原文（注意：客戶版本為 8 點，目前模板僅有 7 點 → 需擴充至 8 點）。
- 文字需保留原始段落順序與標點。
- 客戶原文第 7 點之「因本契約所生之訴訟，雙方合意以 地方法院為管轄法院。」中「以 地方法院」之空格需照樣保留（顯然是要由業主以紙本或加註手寫填入特定地方法院名稱）。
- 客戶原文第 8 點「其他：____________」之底線需在 PDF 上呈現為可手寫之長底線（建議使用既有 `.blank.xwide` 樣式或單純的下底線字元）。
- 若版面空間不足，可調整字級、行距或允許跨頁，但**不得刪減文字**。
- 文字替換後不得出現亂碼、錯別字、重複段落或截斷。
- 客戶原文第 2 點之「為飼主惡意養」疑似缺字／錯字 → 本次**原樣照登**，並列入待確認 Q4 等業主回覆是否要修正（見第 7 節）。

客戶提供原文如下：

```text

1.除本契約另有約定、特殊緊急情況、或不可抗力之情況外，未經飼主同意，店家不得將寵物帶離美容場所（同上店家地址）、轉售、轉讓或以其他變相方法作為其他用途。

2.飼主應於美容當日，將寵物領回，如經通知1日內未領回，依動保法第29條第一款通知主管機關，為飼主惡意養，相關罰金為3萬~15萬元，其他衍生性費用將跟飼主求償，例：人員加班費等。

6.於美容服務期間，如發現寵物有異常狀態，應立即通知飼主並妥善處理，如發生異常狀態的原因，可歸責店家之操作行為，店家應負損害賠償責任，例：摔傷寵物等。

7. 因本契約所生之訴訟，雙方合意以 地方法院為管轄法院。
```

## 5. 資料與 UI 影響

### 5.1 資料模型決議（不變更 schema）

| --- | --- | --- |
| R1 緊急聯絡人選填 | `Owner.EmergencyContactName/Phone/Relationship` 已是 `string`，本來就接受空字串 | 只動 UI 必填驗證 |

## 7. 待確認事項

PM 已就主任 agent 初稿的 4 項議題嘗試解答；標示 [PM 判定] 者為可直接執行，標示 [需業主確認] 者為涉及業務／法律決策、不可單方面判定。本次另補充 Q5、Q6 兩項新發現議題。

### Q1. R2 的「系統上手簽」是否代表完全移除系統內簽名板，或僅代表 PDF 不需嵌入手寫簽名圖？

[PM 判定]：**完全移除系統內簽名板**。
依據：
1. 客戶反饋原文「系統上手簽的地方可以刪除」用詞為「刪除」而非「不要嵌入」，語意傾向移除 UI。
2. 檢視 `contract.hbs` 後確認模板現有簽章欄全為紙本線條設計（`<span class="blank wide">`），並無 base64 簽名圖嵌入區。
3. 配合 R5「簽名線保持空白」與客戶反饋第 4 點「資料表移至第一頁，因每次會變動」可推得客戶定位 PDF 為「列印 → 紙本親簽」之工作流，與螢幕簽名不相容。
→ 結論：移除任何要求飼主於系統內畫布手簽的步驟、控制項與資料寫入；PDF 模板簽名線維持空白。

### Q2. R5 中乙方簽章目前固定顯示「貳寶寵物美容工坊」，是否也需改成空白？

**[業主確認 2026-05-16]：（B）乙方也改空白，由店家於紙本上簽章。**

工程端落實：
- `contract.hbs` 第 240 行 `乙方簽章：<span class="blank wide">貳寶寵物美容工坊</span>` 改為 `乙方簽章：<span class="blank wide"></span>`，與甲方簽章線一致。
- R5 驗收準則應同步擴充：乙方簽章線也需保持空白。

### Q3. R3 若晶片號碼空白時不自動勾選「無」，是否需要新增一個 UI 勾選欄位讓使用者明確表示「無晶片／未登記」？

[PM 判定]：**不新增專用布林欄位，沿用既有 `Pet.UnregisteredIdMethod`**。
依據：
1. `Pet` 已有 `UnregisteredIdMethod : string?` 欄位，且 `contract.hbs` 第 100 行原本就設計「若未登記，身份識別方式：{{pet.unregisteredIdMethod}}」對應此欄位。
2. 新增布林欄位會造成「`ChipNumber` 有值且 `IsUnregistered=true`」這類矛盾狀態之可能性，需要額外驗證邏輯。
3. 以 `UnregisteredIdMethod` 是否有值（非空、非 null）作為「明確標示無晶片」之語意載體即可：使用者若無晶片，至少需填寫一種替代識別方式（含直接填「無」）。
→ 結論：UI 不新增勾選欄位；改於 `ChipNumber` 旁加輔助文字提示。模板渲染：page 1 「若未登記」勾選格判定條件由 `{{#unless pet.chipNumber}}` 改為 `{{#if pet.unregisteredIdMethod}}`；page 4 「無」勾選格採相同判定。

### Q4. R8 原文第 2 點「為飼主惡意養」疑似少字或錯字，是否需原樣照登，或改為業主修正後文字？

**[業主確認 2026-05-16]：修正為「視為飼主惡意棄養」。**

工程端落實：

- 後續 contract.hbs 模板渲染依此修正版本。
- 其他字詞、標點、空格皆維持原文不動。

### Q5（PM 新發現）. R6 是否需支援「異常 + 自由文字補充」？

**[業主確認 2026-05-16]：（B）新增「異常說明」文字欄位並於 PDF 上呈現。**

工程端落實（屬 schema 變更，列為 R6 擴充）：
- `PhysicalExamination` entity 6 個部位各新增一個 `*Note : string?` 欄位（例 `EyesNote`、`EarsNote`、`TeethNote`、`LimbsNote`、`SkinNote`、`FurNote`）。
- UI 在 Pet 編輯頁與 GroomingRecord 填寫頁，當部位選為「異常」時顯示一個短文字框讓使用者輸入說明；選「正常」時隱藏並清空。

### Q6（PM 新發現）. R7 既有 Pet 之 `MedicalHistory = []`（空陣列）是否視為「以上皆無」？

**[業主確認 2026-05-16]：（B）相容 — 空陣列視為「以上皆無」自動勾選。**

工程端落實：
- contract.hbs 第 377–406 行新增「以上皆無」勾選格，渲染條件為：`MedicalHistory` 包含字串 `"以上皆無"` **或** `MedicalHistory` 為空陣列。
- 既有 `data/*.json` 之 Pet 資料無需 migration，空陣列繼續沿用。
- UI 端：使用者勾選「以上皆無」時其他病史 UI 取消、寫入時陣列只含 `"以上皆無"`；使用者取消所有病史勾選時陣列回到 `[]`，PDF 仍會勾「以上皆無」。
- R7 驗收準則調整：明確列出「`MedicalHistory = []`」與「`MedicalHistory = ["以上皆無"]`」兩種輸入皆應於 PDF 上勾選「以上皆無」勾選格。
- 本決定僅適用 R7 病史欄位；R3 晶片欄位仍維持「不自行推論」原則（兩者語意不同：病史空＝臨床上明確無病史；晶片空＝可能尚未登記或拒答）。

### Q7（PM Gherkin 撰寫時新發現）. R6 「異常說明」文字欄位最大長度？

**[業主確認 2026-05-16]：30 字以內，超過截斷。**

工程端落實：
- `PhysicalExamination` 之 6 個 `*Note : string?` 欄位於 UI 與服務端設 `MaxLength = 30`（以 Unicode 字元計）。
- UI 文字框 `MaxLength="30"` 阻止使用者輸入超過 30 字。
- 服務端寫入時若收到超過 30 字（例如匯入舊資料），截斷至前 30 字後存檔。
- PDF 渲染時若 note 超過 30 字仍照樣以前 30 字截斷顯示（保險，理應已截斷）。
- 不需自動折行；30 字內單行可顯示完畢。

### Q8（PM Gherkin 撰寫時新發現）. R6 皮毛 (Fur) 多選與 Note 對應關係？

**[業主確認 2026-05-16]：只在「異常」時顯示說明框；「打結」、「跳蚤壁蝨」為明確分類不需文字說明。**

工程端落實：
- UI：`FurNote` 文字框只在 Fur 包含 `"異常"` 時顯示；包含 `"打結"` 或 `"跳蚤壁蝨"` 但不含 `"異常"` 時，文字框不顯示。
- UI：若 Fur 從含「異常」改為不含「異常」（例如取消「異常」勾選），`FurNote` 自動清空。
- PDF 渲染：`FurNote` 文字只在 Fur 包含 `"異常"` 時輸出；其他狀態不輸出 note 文字（即使 `FurNote` 殘留值，也以 Fur 是否含「異常」為輸出條件）。
- 其他 5 個部位（眼睛/耳朵/牙齒/四肢/皮膚）為「正常/異常」二選一，Q8 規則不適用。

### Q9（PM Gherkin 撰寫時新發現）. 服務當下填的異常說明是否同步回寫到 Pet？

**[業主確認 2026-05-16]：不同步 — 本次服務獨立。**

工程端落實：
- `GroomingRecord.PhysicalExamination` 與 `Pet.PhysicalExamination` 為兩份獨立記錄。
- 美容師於服務當下於 GroomingRecord 填寫的異常與 note 不自動寫回 `Pet.PhysicalExamination`。
- 下次服務新建 GroomingRecord 時，預設值仍從 `Pet.PhysicalExamination` 帶（可能是空白或上一次主檔更新值），由美容師重新評估當下狀態。
- `Pet.PhysicalExamination` 的更新走 Pet 編輯頁專用流程，不被服務紀錄影響。
- PDF 渲染：服務資料表（page 1）以 `GroomingRecord.PhysicalExamination` 為準（已於 R6 主文明定）。
